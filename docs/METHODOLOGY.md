# 项目 AI 协作方法论

> 本文档记录本项目采用的 AI 多智能体协作理论与实践经验，可作为后续类似项目的参考模板。

---

## 一、核心理念

### 一句话概括

**一人一角色，各司其职，逐级上报，闭环交付。**

传统的 AI 助手是一个人包办所有事 —— 既写需求又写代码还做测试，容易顾此失彼、前后矛盾。本项目的做法是模拟一个真实的软件团队，为每个专业领域分配独立智能体，各自聚焦自己的专业，通过严格的协作流程完成交付。

### 五大原则

| 原则 | 说明 |
|------|------|
| **角色分离** | 每个智能体只扮演一个角色，有明确的职责边界，不越界 |
| **单向汇报** | 甲方只与经理对接，经理是唯一的信息汇集点 |
| **直接闭环** | 开发与测试之间直接对接，不经中间层，减少传递损耗 |
| **逐级升级** | 问题先内部解决，解决不了再逐级上报，避免无限循环 |
| **甲方解耦** | 甲方只负责提需求、做决策、最终验收，不参与过程 |
| **测试关卡** | 任何修复或变更必须经测试 agent 验证通过后，经理才能向甲方汇报 |

## 二、团队结构

本项目模拟了一个 7 人软件团队：

```
       甲方（老板）
           ↕
        经理
      ↙  ↓  ↓  ↘
  产品经理  架构师  设计师  运维
              ↘  ↓  ↙
               开发
                ↕
               测试
```

### 角色职责速览

| 角色 | 一句话职责 | 不给谁干活 |
|------|-----------|-----------|
| 产品经理 | 把甲方的大方向细化成完整 PRD | 不写代码、不做设计 |
| 经理 | 分活、收活、汇报，团队唯一对外接口 | 不递活、不写代码、不测试 |
| 架构师 | 技术选型、架构设计、数据库设计、API 设计 | 不写业务代码、不做 UI |
| 设计师 | 视觉规范、页面原型、走查开发实现 | 不写代码、不做后端 |
| 开发 | 按方案和设计稿写代码，修复缺陷 | 不改方案、不做设计 |
| 测试 | 验证功能、反馈缺陷、线上回归 | 不修代码、不做部署 |
| 运维 | 环境搭建、部署上线、配置域名和 SSL | 不写业务代码、不测功能 |

### 关键设计：角色解耦

每个角色都有明确的"你能做什么"和"你不能做什么"。这种边界设计避免了"全能型 AI"的常见问题：
- 同一个 AI 既写需求又写代码时，需求会不自觉地迁就实现难度
- 同一个 AI 既写代码又测试时，容易放过自己写的问题
- 角色分离后，每个智能体只对自己的专业领域负责，形成自然的制衡

## 三、协作流程

### 完整生命周期

```
阶段一：需求规划
  甲方提需求 → 经理转达 → 产品经理细化 PRD → 甲方确认

阶段二：并行启动
  ├─ 架构师：技术方案 + 数据库设计 + API 设计
  ├─ 设计师：视觉规范 + 页面原型
  └─ 运维：服务器环境准备（提前启动）

阶段三：开发实现
  开发：按架构方案 + 设计稿编写代码

阶段四：设计师视觉走查
  设计师检查实现与设计稿一致性 → 不合格退回开发

阶段五：测试闭环（3 轮升级机制）
  测试发现问题 → 开发修复 → 测试验证 （最多 3 轮）
  3 轮未通过 → 架构师换方案 → 再测 3 轮
  仍未通过 → 经理处理 → 再不行 → 甲方决策

阶段六：部署上线
  运维部署 → 配置域名/SSL

阶段七：线上回归测试
  测试在真实域名上验证

阶段八：交付汇报
  测试复测通过 → 经理汇总结果 → 甲方验收
  
  ⚠ 强制规则：经理向甲方汇报前，必须获得测试 agent 的验证通过结论。
    未经测试验证的修复/变更，一律不得汇报给甲方。
```

### 流程设计的关键思想

**1. 并行优先**
运维不需要等开发完成才开始工作。在架构师和设计师出方案的同时，运维就开始准备服务器环境，节省整体时间。

**2. 直接交接，不中转**
开发完成后直接把代码交给测试，测试发现问题直接退回开发。经理不参与中间的传递，减少沟通成本。这就是"经理只分活和收活，不递活"的原则。

**3. 视觉走查前移**
设计师在开发完成后、测试之前就介入检查。如果界面实现跟设计稿不一致，在这个阶段就能发现和修复，避免进入测试后才发现"长得不对"的问题。

## 四、升级机制（四级）

这是本项目最核心的流程设计，解决"问题修不好怎么办"的问题。

| 层级 | 负责人 | 触发条件 | 处理方式 |
|------|--------|---------|---------|
| 第一级 | 开发 + 测试 | 测试发现缺陷 | 直接修复，最多 3 轮 |
| 第二级 | 架构师 | 3 轮未修复 | 换技术方案，同步通知设计师 |
| 第三级 | 经理 | 架构师新方案也未通过 | 重新评估任务，调整安排 |
| 第四级 | 甲方 | 经理判断超出能力范围 | 甲方做最终决策 |

### 升级机制的设计思想

**问题分级，逐级求解。** 每一级先自己想办法，实在不行再往上报。核心逻辑是：

- 开发能修的 bug，不麻烦架构师 → 这是正常的开发迭代
- 架构师能换的方案，不麻烦经理 → 技术问题在技术层面解决
- 经理能协调的，不麻烦老板 → 管理问题在管理层面解决
- 都搞不定的，才上报甲方 → 甲方只需要做关键决策

**3 轮的阈值设计：** 太少了开发来不及修，太多了浪费时间和 Token。3 轮是一个平衡点——足够让开发认真对待，又不会陷入无限循环。

## 五、实操经验总结

### 本项目的实际数据

| 指标 | 数据 |
|------|------|
| 团队规模 | 7 个智能体 |
| 项目周期 | 单次会话，约 3 小时 |
| 总测试用例 | 105 个 |
| 发现缺陷 | 24 个（API 路径不一致 14 个、功能缺陷 10 个） |
| 修复轮次 | 1 轮修复 + 2 轮回归 |
| 最终通过率 | 100% |

### 什么情况下这套方法论有效

- 项目有明确的交付物（网站、应用、文档等）
- 需求可以用"功能清单"来描述
- 技术边界清晰，角色可以独立工作
- 甲方愿意接受"只跟经理对接"的沟通方式

### 什么情况下需要调整

- 极小的项目（如一个脚本）—— 不需要 7 个角色，2-3 个足够
- 需求高度不确定、需要快速试错 —— 升级机制可能太慢，需要更敏捷的方式
- 甲方希望深度参与每个环节 —— 需要调整汇报节点

### 经验教训

1. **前后端 API 路径一致性是最高频的缺陷类型。** 本项目中 14/24 个缺陷都是这个问题。未来可以让架构师在 API 设计阶段就输出一个可被前后端共同引用的常量文件，从源头避免不一致。

2. **设计师走查环节非常有效。** 设计师在开发完成后发现了 14 处不符合野兽派规范的问题，如果这些问题留到测试阶段才发现，测试可能不会标记为缺陷（因为测试只管功能对不对，不管长得好不好看）。

3. **运维提前启动节省了时间。** 虽然运维在本项目中只是输出了部署文档（因为需要甲方提供服务器信息），但文档已经完备，部署时按文档操作即可。

## 六、与其他方法的对比

| 维度 | 传统 AI 对话 | 本项目方法 |
|------|-------------|-----------|
| 角色 | 一个 AI 包办所有 | 7 个专业智能体分工 |
| 需求质量 | 可能遗漏或过度设计 | 产品经理细化 + 甲方确认 |
| 代码质量 | 全看一个 AI 水平 | 架构师方案 + 开发实现 + 测试验证 |
| 界面质量 | 可能粗糙 | 设计师规范 + 视觉走查 |
| 缺陷发现 | 往往靠用户自己发现 | 测试主动发现，闭环修复 |
| 升级机制 | 无，问题可能反复 | 四级升级，不无限循环 |
| 甲方参与 | 全程参与讨论 | 只参与需求、决策、验收 |
| 部署 | 通常不涉及 | 运维提供完整部署方案 |
